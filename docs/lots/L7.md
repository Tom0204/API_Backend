## Choix de réalisation

| Sujet | Choix |
|---|---|
| Contrôle unique | `assertPermission` (`identity/app/utils`) appelé par `authenticate(token, permission?)`, qui relit session et compte à chaque requête ; une seule lecture par requête |
| Middleware | `createAuthGuards` (`identity/api/require-auth.ts`) fournit `requireAuth` et `requirePermission(p)` ; un seul fichier au lieu de `require-permission.ts` prévu à l'audit |
| Routes de jeu | `app.ts` construit `requirePlayer = requirePermission('PLAY')` ; les contextes de jeu reçoivent `requirePlayer` (ex-`requireAuth`) sans connaître identity |
| Garde-fous | Soi-même et hiérarchie dans `Account.suspend/reactivate/changeRole` ; la permission de l'action reste contrôlée par la route |
| Suspension | Compte verrouillé (`findByIdForUpdate`), puis `revokeAllByAccount` dans la même transaction, comme `logout-all` : mise à jour groupée, sans règle propre aux sessions |
| Entrée des actions | `accountId` = acteur (contexte d'authentification), `targetAccountId` = compte visé |
| Seed | `src/platform/prisma/seed-admin.ts` : configuration lue avant toute écriture, `upsert` sans mise à jour |
| Migration | `20261130090000_roles` (horodatage aligné sur les migrations précédentes) ; CHECK `accounts_permissions_known_bits` |

## Points restants

- Risque accepté : la permission de l'acteur est contrôlée par `authenticate`, dans une transaction distincte de l'action. Un acteur rétrogradé à cet instant précis peut encore agir une fois. Deux administrateurs peuvent aussi se suspendre mutuellement en parallèle et ne laisser aucun administrateur actif (le seed ne recrée pas un compte existant).
- `GET /api/v1/admin/accounts` renvoie tous les comptes, sans pagination (D8) : la réponse grossit avec la base.
- 403 pour une cible plus privilégiée contre 404 pour un compte inexistant : l'existence est révélée, ce qui reste sans effet tant que `ACCOUNTS_SUSPEND` va avec `ACCOUNTS_READ`.
- E2 : les actions d'administration ne sont pas tracées.
