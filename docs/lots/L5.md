## Décisions validées

| # | Question | Décision |
|---|---|---|
| D1 | Comment la réponse finale récupère XP et butin (`rewards`, L4 D2) ? | Les handlers publient à leur tour `ExperienceGranted` et `LootAwarded` ; `publish` renvoie les événements produits pendant la cascade, et le combat compose `rewards` à partir d'eux |
| D2 | `CharacterCreated` et `CombatStarted` ont besoin d'un identifiant attribué par PostgreSQL | Le cas d'usage enregistre ces deux événements juste après l'insertion |
| D3 | Qui possède le journal ? | Nouveau contexte `journal` (domaine, handler, repository) ; PROD-01 le lira par contrat |
| D4 | Granularité des tours journalisés | Un `CombatTurnPlayed` par attaque (ouverture, attaque, riposte) : attaquant, dégâts, PV restants des deux participants |

Choix d'implémentation (imitation de `docs/architecture.md`) :

- Port de publication dans `shared/app` ; publieur (file FIFO, registre ordonné, limite de profondeur) dans
  `platform/events/` ; `events` ajouté à `AppTransaction`, construit sur les repositories de la même transaction.
- Handlers `(event, transaction)` dans `contexts/X/app/handlers/` ; chaque contexte récepteur déclare dans ses
  `app/interfaces` la forme d'événement attendue (typage structurel, aucun import entre contextes).
- Ordre d'enregistrement fixe : characters → inventory → journal.
- Date des événements : le `now` déjà passé aux méthodes de l'agrégat (issu de `Clock`).
- Table `game_events` : identifiant, type, personnage (cascade), combat (facultatif), données JSON, date.
- XP et butin : les handlers lisent les données du monstre par deux contrats fournis par world
  (`MonsterExperience`, `LootTables`, qui garde la règle r < p) ; `CombatWon` ne porte que des identifiants.
- `RandomSource` passe du cas d'usage `PlayCombatAction` au handler de butin (`createEventHandlers({ random })`) ;
  `CreateCharacter` reçoit `Clock` pour dater `CharacterCreated`.
- Supprimés : `grant-victory-rewards.ts`, contrat `CombatLoot` et son service, `CombatFighters.grantExperience`,
  `xpReward` et `rollLoot` de `Opponent`.
- Migration générée sous `20261126085325_game_events`, renommée `20261128090000_game_events` pour suivre
  `inventory` ; relue (CHECK données objet et type non vide ajoutés à la main), appliquée à `mmorpg_dev`
  (2 comptes, 2 personnages, 2 combats conservés ; leurs combats passés n'ont pas d'entrée de journal).
