## Décisions validées

| # | Question | Décision |
|---|---|---|
| D1 | Où vit l'historique ? | Cas d'usage dans `combat` (propriété par `ensureCombatOwnedBy`) ; contrat `CombatJournal.turnsOf(combatId)` satisfait par un service de `journal` (filtre `CombatTurnPlayed`, garde de forme), relié dans `platform/transaction.ts` (L5 D3) |
| D2 | Forme de l'historique | `data: { combatId, status, turns: [{ number, attacker: CHARACTER\|MONSTER, damage, characterHp, monsterHp }] }` ; uniquement les coups ; un combat antérieur à L5 renvoie `turns: []` |
| D3 | Pagination du classement | `?limit=` de 1 à 100 (20 par défaut), `?offset=` ≥ 0 (0 par défaut) ; `data` reste un tableau ; `rank = offset + index + 1` ; pas de `total` |
| D4 | Départage et contenu du classement | Tri `level DESC, experience DESC, createdAt ASC, id ASC` ; champs `rank, name, classId, level, experience` (ni `id`, ni `accountId`) ; permission `PLAY` ; index ajouté par une migration |
| D5 | Comptes suspendus dans le classement | Leurs personnages sont inclus : aucune jointure sur `accounts` depuis `characters` |
| D6 | Production de la spec | Document TypeScript dans `platform/http/openapi/` ; schémas tirés des schémas Zod par `z.toJSONSchema` ; enveloppes de succès et d'erreur en `components` ; dépendance `swagger-ui-express` (+ `@types/swagger-ui-express`) |
| D7 | Exposition de `/docs` | Publique, hors `/api/v1`, sans limitation de débit (comme `/health`) ; désactivée quand `NODE_ENV=production` |

Choix d'implémentation (imitation de `docs/architecture.md`) :

- Classement dans le contexte `characters` : `CharacterRepository.findLeaderboardPage`, cas d'usage de lecture `GetLeaderboard`,
  routes `leaderboard.*`. Borne technique `offset` ≤ 1 000 000 (au-delà, 400) pour ne jamais transmettre un entier démesuré.
- Le schéma de requête accepte aussi un entier déjà converti : la route relit `req.query` après `validate`, qui l'a remplacé.
- Migration générée sous `20261126111706_leaderboard_index`, renommée `20261201090000_leaderboard_index` pour suivre
  `roles` ; un seul `CREATE INDEX`, appliquée à `mmorpg_dev` (2 comptes, 2 personnages, 2 combats conservés).
- Historique : ordre du journal (date, puis UUID v7) ; coups numérotés à partir de 1 ; entrée mal formée → 500.
- OpenAPI : corps issus de `z.toJSONSchema` (`io: 'input'`), paramètres de chemin UUID déduits du chemin, réponses d'erreur
  en `components.responses`, données décrites une fois par présentateur dans `openapi-schemas.ts` ; Swagger UI sans
  badge de validation externe (CSP de Helmet inchangée).
- `AppOptions.apiDocs` : vrai dans `buildTestApp`, `NODE_ENV !== 'production'` dans `main.ts`.

## Points restants

- Mineurs de la revue complète, antérieurs au lot, non corrigés (hors périmètre) :
  - verrou `FOR UPDATE` pris avant le contrôle de propriété (`combat-fighters.ts`, `play-combat-action.ts`) : léger écart de délai entre ressource d'un autre joueur et ressource inexistante ;
  - identité du jeton étalée avant le corps (`combat.routes.ts:31`, `character.controller.ts:24`) : protégé par `z.strictObject`, mais l'ordre inverse serait plus sûr ;
  - erreurs `request.aborted` / `request.size.invalid` de body-parser traduites en 500 (`error-handler.ts`) ;
  - `err` journalisé avec son message : un message d'erreur Prisma pourrait citer des arguments (non confirmé) ;
  - acteur d'une action d'administration lu sans verrou (`find-administrable-account.ts`) : fenêtre de quelques millisecondes.
- Non vérifié par la revue : messages réels des erreurs Prisma 7, `trust proxy` derrière un reverse proxy.
- QUAL-02 : Runner Postman (L1 à L8) non exécuté par l'agent, à lancer sur une base fraîchement initialisée.
- `npm audit` : 4 alertes antérieures au lot (`effect` via `prisma`, `esbuild`), sans lien avec `swagger-ui-express`.
- Doublon YAML `postman/collections/` (L1 à L4) et dossier vide `New Collection/` signalés, non modifiés (E2).
