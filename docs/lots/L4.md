## Décisions validées

| # | Question | Décision |
|---|---|---|
| D1 | Stockage de l'inventaire | Table `inventory_items (character_id, item_id, quantity CHECK > 0)`, clé primaire composée, cascade sur le personnage ; aucune ligne = inventaire vide ; ajout atomique `ON CONFLICT DO UPDATE quantity = quantity + 1` |
| D2 | Récompenses dans la réponse | Champ `rewards` ajouté au combat : `{ experienceGained, levelsGained, level, experience, item: { id, code, name, quantity } \| null }`, non persisté ; `null` hors de l'action finale victorieuse (comme `lastTurn`) |
| D3 | Forme de `GET /api/v1/characters/:characterId/inventory` | `data` = tableau `[{ itemId, code, name, quantity }]` trié par nom ; `[]` si vide |
| D4 | Parcours Postman | Victoire guerrier contre loup (25 XP, butin aléatoire accepté), défaite mage contre bandit, inventaire consulté ; attaque en boucle (`setNextRequest`) ; Runner lancé par l'utilisateur, parcours rejoué en `curl` par `/verifier` |

Choix d'implémentation (imitation de `docs/architecture.md`) :

- `PlayCombatAction` : verrou sur le combat, puis sur le personnage (`findByIdForUpdate`) ; à la victoire, XP, tirage
  du butin (port `RandomSource`) et ajout à l'inventaire dans le même `UnitOfWork`. Ordre des verrous : combat → personnage.
- Une seule attribution : transition `IN_PROGRESS → VICTORY` sous verrou ; une seconde action lève `COMBAT_FINISHED`.
- `RandomSource.next()` dans [0, 1[, implémenté par `crypto-random-source.ts` (6 octets / 2^48), comme le prévoit
  `docs/architecture.md`. Le premier essai avec `randomInt(2 ** 48)` levait une `RangeError` (500), défaut trouvé par le
  test manuel et couvert depuis par `tests/unit/infrastructure/crypto-random-source.test.ts`.
- Niveau 10 : XP ignorée (rules.md §5), butin toujours tiré. **Hypothèse :** `experienceGained` vaut l'XP fixe du
  monstre même au niveau 10 (la progression l'ignore) ; aucune règle ne précise ce qui est affiché.
- `Inventory` mémorise ses ajouts (`pendingAdditions`) ; le repository les écrit par incrément atomique.
  L'agrégat sert à une seule écriture par transaction.
- Migration générée sous `20261125133537_inventory`, renommée `20261127090000_inventory` pour rester après `combats` ;
  relue (CHECK `quantity > 0` ajouté à la main), `mmorpg_dev` vide, puis appliquée.
